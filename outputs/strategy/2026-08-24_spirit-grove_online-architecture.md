# Spirit Grove 온라인 방향 설계문서

작성 2026-08-24 · 근거: 코드 실측(단일 HTML·GitHub Pages 정적 배포·`serialize`/`serMon` 저장 포맷·클라이언트 신뢰 상태·기존 코드/QR 교환·핫싯 대전) · 목적: **온라인(대전·교환·리더보드) 도입 전 아키텍처 결정을 준비**

> 이 문서는 **코드가 아니라 의사결정 자료**다. 아래 「§7 결정해야 할 것」의 4개 항목을 정하면 Phase 별 구현으로 넘어갈 수 있다.
> 비용 수치는 **자릿수 감(感)** 이며, 정확한 요금·무료 티어는 시점에 따라 바뀌므로 착수 직전 재확인한다(⚠️ 확인 필요 표시).

---

## 1. 왜 지금 이 문서인가

로컬로 완결 가능한 로드맵 항목(H1~H4의 타입·개체값·교배·서사·핫싯 대전·코드/QR 교환·업적·데일리)은 **모두 구현됐다.**
남은 소셜 축 — **온라인 대전 · 온라인 교환 · 리더보드** — 은 셋 다 **서버가 있어야** 완성된다. 단일 HTML·정적 호스팅
아키텍처에 서버를 어떻게 붙이느냐가 이 프로젝트의 다음 큰 갈림길이고, 잘못 고르면 운영 부담·비용·락인이 오래 남는다.

## 2. 현재 아키텍처의 제약 (출발점)

| 항목 | 현재 상태 | 온라인화에 주는 제약 |
|---|---|---|
| 호스팅 | **GitHub Pages(정적)** — Actions가 `build.py` 산출물을 배포 | 서버 로직을 여기 둘 수 없다. **별도 백엔드**가 필수 |
| 배포 산출물 | **자립형 단일 HTML** (assets 인라인) | 클라이언트는 그대로 두고 **네트워크 계층만 얹는** 설계가 유리 |
| 저장 | `localStorage` + `serialize()`(v:4) / `deserialize()` | 이미 **직렬화 포맷이 있다** → 클라우드 세이브·교환 페이로드로 재사용 가능 |
| 상태 신뢰 | **전적으로 클라이언트 신뢰**(세이브·교환코드 위조 가능) | 경쟁성 기능은 **서버 검증** 없이는 치팅에 무방비 |
| 계정 | **없음**(익명 로컬) | 온라인은 최소한의 **식별자/계정**이 필요 |
| 기존 소셜 | 코드/QR 교환(수동), 핫싯 대전(로컬) | 온라인은 이 둘의 **"수동/로컬"을 "원격/자동"으로** 올리는 것 |

**핵심 통찰:** `serMon`/`reviveMon`(교환 코드에서 검증됨)과 전투 엔진(`dbExec` 등 순수 함수)이 이미 있으므로,
온라인은 대체로 **"메시지 전달 + 약간의 검증"** 문제로 환원된다. 풀 게임서버를 새로 짤 필요는 낮다.

## 3. 백엔드 선택지 비교

| 옵션 | 형태 | 실시간 | 비용(자릿수·⚠️확인) | 운영 부담 | 락인 | 이 프로젝트 적합도 |
|---|---|---|---|---|---|---|
| **A. BaaS (Supabase / Firebase)** | 관리형 DB+인증+실시간 | ○(Realtime/Firestore 구독) | 취미 규모 **무료 티어 내** 가능 | 낮음 | 중(SDK 종속) | ★★★ 교환·리더보드에 최적 |
| **B. Cloudflare Workers + Durable Objects/KV** | 엣지 서버리스 | ◎(WebSocket/DO) | 저렴(무료 티어 넉넉) | 낮음 | 중 | ★★★ 실시간 대전에 최적 |
| **C. REST + 관리형 Postgres(Neon 등)** | 얇은 API 서버 | △(폴링) | 저~중 | 중 | 낮음 | ★★ 범용이나 실시간 약함 |
| **D. P2P WebRTC(+시그널링만 서버)** | 클라 직결 | ◎ | 시그널링만 → 매우 저렴 | 중(NAT/TURN) | 낮음 | ★★ 1:1 대전엔 매력적, 비동기·순위엔 부적 |
| **E. 자체 호스팅 VPS(Node)** | 풀 컨트롤 | ◎ | 고정비 상시 | **높음** | 낮음 | ★ 1인 취미엔 과함 |

**단일 HTML 제약과의 정합:** A·B·D는 클라이언트에 SDK/소량 코드만 얹으면 되고 정적 호스팅을 유지한다.
E는 게임까지 옮겨오고 싶은 유혹이 있으나 운영이 무겁다. **A(교환·순위) + B(실시간 대전)** 조합이 제약에 가장 잘 맞는다.

## 4. 트랙별 요구와 매핑

### 4-1. 온라인 교환 (가장 쉬움 · 먼저)
- 지금: `tradeCodeFor`/`parseTradeCode`로 **코드를 사람이 직접 전달**. 온라인화 = **코드를 클라우드에 올리고 친구가 코드 없이 받기**.
- 최소 형태: "교환 보관함" 테이블에 `serMon` JSON + 6자리 코드/친구ID로 put → 상대가 get → 원본 삭제(1회성).
- 적합: **A(BaaS)**. 실시간 불필요(비동기). 무료 티어로 충분.
- 난제: **복제 방지**(현재 코드 교환은 '선물/복제'다). 진짜 교환이면 서버가 "출고 시 원본 소각"을 **원자적으로** 보장해야 → 서버 권위 필요.

### 4-2. 온라인 대전 (중간~어려움)
- 지금: 핫싯(한 기기 2인). 온라인화 = **두 기기가 턴을 주고받기**.
- 두 갈래:
  - **(a) 비동기/캐주얼**: 팀 코드 교환 후 각자 시드 고정 시뮬 or 턴 메시지 릴레이. 라이트, 치팅 허용(친선).
  - **(b) 실시간 턴제**: WebSocket으로 턴 교환. **B(Workers+DO)** 나 **D(WebRTC)**.
- 치팅: 전투 로직이 클라에 있으므로 **경쟁전은 서버 권위(server-authoritative) 재계산**이 필요. 친선전은 명예제(honor-system)로 수용 가능.

### 4-3. 리더보드 (쉬움이나 치팅 취약)
- 후보 지표: **연전 도장 최고 연승(`towerBest`)**, 업적 달성 수, 도감 완성 시간.
- 최소 형태: `POST score` → 랭킹 read. **A(BaaS)** 로 즉시 가능.
- 난제: 클라 신뢰 상태라 **점수 위조가 자명**. 대책 단계: (1) 명예제+명백한 이상치 컷 → (2) 서버 재현 가능한 리플레이 제출 → (3) 서버 권위 전투. 1인 취미 규모면 **(1)로 시작**이 현실적.

## 5. 공통 난제 (트랙 불문)

1. **계정/식별** — 최소 익명 계정(기기 로컬 키) → 선택적 소셜 로그인. 교환·순위엔 안정적 ID가 필요.
2. **안티치트** — 근본적으로 클라 신뢰 구조. *경쟁성의 수준을 먼저 정하고* 거기에 맞는 최소 방어만 넣는다(과투자 금지).
3. **클라우드 세이브** — `serialize()`가 있으니 부수입으로 얻기 쉽다. 기기 간 이어하기 = 재방문/리텐션에 큰 값.
4. **개인정보·약관·미성년자** — 계정·랭킹은 최소 개인정보라도 **처리방침/약관**이 필요(특히 아동 대상성 게임이면 주의).
5. **비용 상한·남용 방지** — 무료 티어 초과·악성 트래픽 대비 **레이트리밋과 상한**을 처음부터.
6. **버전 정합** — 클라 배포가 잦다(Pages 자동배포). 서버-클라 **스키마 버전 협상**(교환 코드에 이미 `SGT1`, 세이브에 `v:4` 있음 — 확장).

## 6. 권장 로드맵 (단계적·되돌릴 수 있게)

> 원칙: **작고 치팅 내성이 낮아도 되는 것부터**. 각 단계는 독립 출시 가능하고, 다음 단계가 앞 단계를 무르지 않는다.

- **Phase 0 — 클라우드 세이브 + 리더보드(read 위주)** · 옵션 A · 노력 小
  - 익명 계정 + `serialize()` 업로드/복원, `towerBest` 랭킹(명예제 + 이상치 컷). 온라인의 "발판"을 최소비용으로.
- **Phase 1 — 비동기 온라인 교환** · 옵션 A · 노력 中
  - 코드 없이 친구 교환. **서버 권위 소각**으로 복제 방지(진짜 교환). 기존 `serMon` 재사용.
- **Phase 2 — 실시간 친선 대전** · 옵션 B 또는 D · 노력 中~大
  - 핫싯 UI를 네트워크 턴 교환으로. 친선전은 명예제. `dbExec` 재사용.
- **Phase 3 — 경쟁 대전 + 랭크(선택)** · 옵션 B(서버 권위) · 노력 大
  - 서버가 전투를 재계산/검증. 안티치트·매치메이킹·시즌. **수요가 확인된 뒤에만** 착수.

각 Phase 전에 §7을 재확인한다. Phase 0~1만으로도 "온라인 게임"의 체감 대부분(이어하기·순위·원격 교환)을 확보한다.

## 7. 결정해야 할 것 (사용자 입력 필요)

1. **계정 방식** — (a) 익명 기기키만 / (b) 익명 + 선택적 소셜 로그인 / (c) 처음부터 로그인 필수. → 개인정보·리텐션·복잡도 트레이드오프.
2. **비용 상한** — 월 상한 얼마까지 수용? (무료 티어 내 유지가 목표인지, 소액 유료 감수인지). → 옵션·트래픽 설계 좌우.
3. **경쟁성 수준** — 대전/순위가 (a) 친선·명예제로 충분 / (b) 진지한 랭크 필요. → 안티치트 투자량(Phase 3 착수 여부) 결정.
4. **우선 트랙** — 교환 먼저 / 대전 먼저 / 이어하기+순위(Phase 0) 먼저. → 권장은 **Phase 0 → 교환**.

## 8. 리스크·주의

- **안티치트에 과투자 금지** — 경쟁 수요가 검증되기 전 서버 권위 전투(Phase 3)에 들어가면 노력 대비 회수 위험. 명예제로 시작.
- **락인 최소화** — DB 스키마·직렬화를 **BaaS 비종속 형태**(우리 `serialize` 포맷 그대로)로 저장하면 옵션 교체가 쉽다.
- **정적 호스팅 유지** — 게임 자체는 계속 Pages에. 서버는 **API/실시간만** 담당(클라 자립성·오프라인 우선 유지).
- **오프라인 우선 불변식 보존** — 온라인은 **부가 기능**이어야 한다. 네트워크가 없어도 게임 전체가 지금처럼 돌아가야 한다(회귀로 못박기).
- **개인정보/약관 선행** — 계정·랭킹 출시 전 최소 처리방침 필요(법률 확인은 범위 밖 · ⚠️ 확인 필요).

## 부록 — 재사용 가능한 기존 자산 (온라인화 지렛대)

- `serialize()`/`deserialize()` (세이브 v:4) → **클라우드 세이브 페이로드** 그대로.
- `serMon`/`reviveMon` (교환 코드에서 왕복 검증됨) → **교환 오브젝트** 그대로.
- `tradeCodeFor`/`parseTradeCode` + 체크섬 → **서버 경유 교환의 클라 측** 재사용.
- 전투 엔진 순수 함수(`dbExec`/`damage`/`effSpd` 등) → **서버 권위 재계산(Phase 3)** 시 동일 로직 이식 가능.
- `towerBest`/`achClaimed`/`playSec` → **리더보드 지표** 즉시 사용.
